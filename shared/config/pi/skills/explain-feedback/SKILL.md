## When to Use
Load automatically when producing human-facing feedback about a product, implementation, design, architecture, or technical proposal, especially when recommending a change or questioning a decision. This includes follow-up recommendations after an investigation, turning findings into a comment, and shortening or revising an earlier draft; the user need not call it feedback or name the skill. Apply both to a single comment and to findings within a larger review, across chat, GitHub, Slack, and documents. A request for 'one comment' constrains delivery, not the reasoning that must survive. For a straightforward correctness bug, a short evidence → consequence → fix explanation is enough. Neutral summaries, routine status, implementation-only work, and interpersonal/performance feedback are outside this workflow. It owns explanation, not the underlying review or investigation, and grants no permission to run tests, edit code, or post messages. Run the comprehension gate below on each substantive draft or revision, even when the skill was loaded earlier in the conversation.

## Procedure
1. Read the user's request and establish the recipient, delivery surface, and decision the feedback must help them make. Retain enough context that the recipient need not have seen the preceding conversation. Follow applicable project instructions, including attribution and posting authorization. Use a technical-writing-style skill if available for general prose guidance; this skill adds the reasoning needed for feedback.
2. Before polishing wording, identify what is established by the supplied evidence, what is an inference or preference, and what remains unknown. Use evidence already gathered; do not automatically start a new investigation or test run. If a missing fact could reverse the recommendation, narrow the claim, make the recommendation conditional, or ask a focused question. Never invent customer behavior, motivations, measurements, or security guarantees to strengthen the argument.
3. For a product or architecture choice, read references/examples.md relative to this SKILL.md before drafting. Its fictional weak and stronger comments demonstrate the target reasoning depth, not a required paragraph count or a reusable policy decision.
4. Find the strongest real reason for the current approach. Name the problem it solves and the flexibility or simplicity it preserves. Describe a structural advantage as an inference when appropriate, not as invented development history or author motivation. This is analysis, not a praise sandwich: omit generic compliments, and do not manufacture a benefit for a clearly incorrect implementation.
5. Trace the concrete downside from behavior to consequence: what does the user or maintainer encounter, what decision or failure does it produce, and why does that matter? Use a specific case from the evidence. Translate abstractions such as 'cognitive load', 'consistency', or 'maintainability' into observable work, confusion, risk, or duplicated responsibility. A principle can support the reasoning but cannot replace it.
6. Evaluate an alternative against the same goal. State what it improves and the meaningful capability, discoverability, setup effort, operational burden, or flexibility it sacrifices. Explain why that tradeoff is worthwhile for this case. Do not merely list pros and cons; make a recommendation when supported. Name a condition or piece of evidence that would materially change the recommendation, if one exists.
7. Compose one coherent argument in the requested format. Start with the problem the recipient needs to understand; introduce implementation details when they explain its cause or the proposed remedy. Define unfamiliar terms by what they do before relying on names or shorthand. A consequential decision often needs: current benefit and concrete concern; a worked tradeoff; a preferred approach with its limits; a specific ask. Keep causal links in prose when that makes them easier to follow. Use bullets only when they clarify independent findings, without mandatory headings or a fixed paragraph count.
8. Finish with an actionable change or an explicit decision that needs an owner. Include ownership or source-of-truth placement only when it prevents the problem from recurring; do not bury the product argument under implementation machinery or demand a generalized framework for a local fix. Preserve flexibility when the evidence supports more than one valid choice.
9. Apply the **comprehension gate** before returning each draft, including follow-up rewrites: could a recipient without this conversation explain (a) what happens today, (b) a concrete failure or cost and why it occurs, and (c) how the requested change addresses it? For a consequential choice, they must also understand the alternative's meaningful cost and why it is worth accepting here. If the draft only names a pattern, cites a principle, or gives an instruction, supply the missing causal explanation before returning it. Cut repetition, test narratives, generic opening praise, and process display before cutting reasoning; shortening is not permission to remove the argument. Check claims against the evidence so editing does not increase certainty. If asked only to draft, return the draft without posting it.

## Pitfalls
- A polished prescription is still weak feedback: 'keep an explicit Save button and let the product owner decide' states the ask but does not explain the tradeoff.
- Do not make an opinion sound evidence-backed by adding persuasive prose. Improve or qualify the judgment before improving its presentation.
- Do not force balance around a deterministic bug, invent equal merits for unequal options, or append caveats that would change no action. Calibrate depth to consequence and uncertainty.
- Do not assume a simpler interaction has no cost. Explain which user capability, visibility, control, or recovery path the proposed simplification would remove.
- Do not treat current behavior or historical compatibility as proof of an intentional product decision. Explain why the proposal fits the task people need to complete.
- Do not substitute slogans ('reduces friction', 'one source of truth') for the concrete mechanism and cost. Explain who does extra work, what can go wrong, or which decisions can disagree.
- Do not compress a substantive decision into terse bullets just because the user requests one comment. Do not pad a simple finding into a multi-section essay either.
- Do not mechanically imitate the sample's wording or always prefer explicit confirmation over automatic updates. The example teaches a method of evaluating a choice, not the choice itself.
- For reusable or public reference examples, invent independent scenarios and label their assumptions. Do not quote private review exchanges or merely rename the participants while preserving internal implementation details.
- Do not start tests, edit code, or publish a draft merely because the feedback suggests a change. This skill changes how feedback is explained, not what actions are authorized.

## Verification
1. The description and When to Use cover explicit comment drafting, implicit critique/recommendation requests, revising terse feedback, and translating findings for an author, across code, product, UX, and architecture contexts.
2. Every material factual claim is supported by supplied evidence; recommendations, inferences, and decision-changing unknowns remain distinguishable.
3. The final draft passes the comprehension gate—not merely a checklist in the agent's reasoning. The cold reader can explain today's behavior, a concrete consequence and its cause, and how the proposed change prevents it. A consequential choice also explains its real tradeoff and any condition that would reverse the judgment; a deterministic bug needs only evidence, impact, and fix.
4. The recipient has a specific next action or decision. The comment does not require reconstructing the preceding conversation to understand it.
5. The output fits the requested delivery surface without forced headings, formulaic praise, repetition, unsupported confidence, or unnecessary implementation detail.
6. The saved skill has valid frontmatter and a portable relative reference to references/examples.md. Check routing examples for follow-up recommendations, comment conversion, and shortening, alongside neutral summary/status near-misses. Distinguish static checks and sample runs from measured automatic invocation; loading the skill alone does not prove that its comprehension gate was applied.
